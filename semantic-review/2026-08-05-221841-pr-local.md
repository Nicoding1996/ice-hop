# SDK-compatible transactional progression repair (final review)

The repair adapts authoritative Daily, Endless, and Community transactions to Devvit 0.12.24, whose `TxClient.exec()` omits boolean replies. WATCH-protected pre-reads preserve conditional-write semantics while a queued non-boolean write distinguishes commit from abort. The surrounding client and route changes close the previously identified lifecycle, counting, telemetry, resize, historical-post, and test-double gaps. No behavioral release blocker remains.

**Watch for:** **confirmed** (non-blocking) — the Redis doubles support transactional `hSet` but intentionally return a more complete EXEC result array than Devvit 0.12.24; production compatibility is enforced by requiring a surviving non-boolean write and treating `[]` as the WATCH-abort signal.

**Verdict**: APPROVED

## High-level view

The installed 0.12.24 `TxClient.exec()` parser ignores `TransactionResponse.bool`. Every transaction using the relaxed commit check queues at least one HSET or sorted-set write whose numeric result survives the parser, while current WATCH-abort handling returns an empty result. Each overwrite-capable HSET remains guarded by a watched absence/state check; the server-generated UUID reservation is also verified by reading its exact field after commit.

Signed Endless issuance reserves bounded capacity before consuming a pool board, finalizes the exact board into that reservation, and releases failed or abandoned reservations. Client shutdown releases both active and warmed issues unless the explicit Next transition preserves the prefetch for the replacement GameScene instance.

First Endless completion is derived from the permanent per-tier ledger and returns `counted: true` only to its creator transaction. Community `firstSolve` comes from played membership rather than score improvement, preventing retries from inflating creator solves or telemetry. Client telemetry is allowlisted, daily-rate-limited with HTTP 429, and non-success responses remain best-effort.

GameScene clears board-derived state before asynchronous loading, preventing resize from repainting a previous puzzle. Post resolution checks UGC and host-post Daily mappings before the current canonical fallback, retaining historical board identity. Transactional HSET is present in the repaired doubles, though their EXEC output shape remains more complete than the real SDK’s.

## EXEC compatibility retains WATCH-enforced exclusivity

The installed `@devvit/redis` 0.12.24 implementation maps members, nil, numeric, string-list, string, and double transaction responses but has no branch for `result.bool`. An HSET followed by EXPIRE can therefore produce `[0]` or `[1]` even though both commands committed.

`src/server/core/completion.ts` applies `Array.isArray(result) && result.length > 0` only to this SDK-specific transaction family. Daily play issuance, Endless reservation/finalization, hint claiming, and completion claiming always queue HSET; Community evidence always queues ZADD and its projection always queues HSET. No current caller can reach EXEC with EXPIRE as its only operation.

Replacing watched HSETNX with HSET does not create an overwrite race. Daily issuance checks the watched `play` field; finalization checks that the issue remains reserved; hint/completion claims inspect watched resolution and ledger fields; Community credit inspects watched played and credit indexes. A competitor changes a watched key and forces a retry against the new state. Reservation uses a fresh UUID, checks watched hash capacity, and re-reads its field after commit.

`src/server/core/leaderboard.ts` retains exact result-cardinality checks because its queued SET, ZADD, and ZREM replies are represented by the SDK; the relaxed interpretation is not applied globally.

## Endless reservations survive Next and disappear on abandonment

```
GET /api/endless
  -> reserve user issue slot
  -> pop/generate board
  -> finalize exact board + par
  -> disclose issueId

abandon current/prefetch -> release temporary issue
verified completion      -> write permanent ledger -> release temporary issue
lost completion response -> retry from ledger      -> counted: false
```

`src/server/routes/api.ts` reserves before pool consumption and releases any acquired issue on failure. `src/server/core/completion.ts` watches the capped per-user issue hash during reservation/finalization, carries the reservation timestamp into the issued record, and keeps permanent ledgers independent from temporary cleanup.

`GameScene` releases an unfinished active issue and any warmed registry issue on shutdown. The Next button alone sets `preserveEndlessPrefetch` before fading; shutdown keeps the stash, the reused scene resets the flag in `init`, and `takeOrFetchEndless` consumes the matching issue. Late or losing prefetch responses are generation-checked and released.

A solve captures its issue ID and transcript before scene reuse. If Next is tapped during completion, the old response still merges progression monotonically; success removes the old issue server-side, while failure releases the captured old issue without touching the warmed Next issue.

## First-solve effects and telemetry remain one-time

Endless completion watches resolution, tier ledger, and Hard-at-par metadata together. `ledgerAdded` is true only for the commit that creates the permanent ledger field. Stats derive total progression from baseline plus ledger cardinality, so the first solve displays one and a retry returns the same total with `counted: false`.

Community completion watches candidate, played, and credit state. `firstSolve` means the played index did not contain the puzzle, independent of score improvement. Candidate evidence, played membership, creator credit, and creator solve increment commit together. Legacy played rows seed only the marker; concurrent or repeated completions return `firstSolve: false`.

Endless telemetry runs only for `ledgerAdded`, Community telemetry only for `firstSolve`, and signed Daily telemetry only for a new date claim. Client events pass through an allowlist and per-actor daily counter; requests beyond 500 return 429. `trackClientEvent` neither throws nor logs non-OK responses, so telemetry limiting cannot interrupt play or emit an application warning.

## Scene reuse and historical posts no longer select stale content

`GameScene.init` clears `board`, pieces, par, date, transcripts, issue IDs, and overlay state before loading. The resize callback returns while `board` is absent; recap and win resizes fit the existing blocking overlay instead of rebuilding the board.

Both `/api/post-preview` and `/api/init` resolve host-post UGC first, then the host post’s Daily mapping, and only then the current canonical Daily. Raw historical dates normalize to the legacy schema, new mappings carry schema-qualified IDs, and a missing archived board fails closed instead of generating different content under old progression keys.

## Regression coverage and validation

The completion and Community doubles now implement transactional HSET with version bumps. Existing cases cover bounded reservation/release, first Endless counting, ledger-backed retries, Community firstSolve races, legacy credit migration, and WATCH aborts.

**Confirmed** (non-blocking): those doubles return one value per queued operation, so they do not directly model the SDK dropping an EXPIRE boolean. An explicit `[0]` commit versus `[]` abort case would protect the compatibility invariant.
